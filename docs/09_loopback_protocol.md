# 루프백 프로토콜

## 일반 원칙
- 임의의 하위 단계에서 상위 단계로 루프백 가능
- AI가 도달 가능한 모든 루프백 대상을 평가하여 사유+예상 효과를 사용자에게 제시, 컨펌 받음
- 루프백 시: stages/는 변경 부분만 갱신, 사유를 최상단에 기록, 산출물은 새 run 번호로
- 루프백 전 반드시 pivot_diagnosis_card.yaml 작성

## 진단 프로토콜 (diagnose 패턴)
pivot_diagnosis_card.yaml에 다음 5항을 기록:
1. **시도한 것**: 어떤 실험/분석을 수행했는가
2. **실제 결과**: 무엇이 일어났는가 (구체적 수치 포함)
3. **기대한 것**: 무엇을 예상했는가 (타겟 기준)
4. **원인**: 2와 3의 차이를 만든 근인은 무엇인가
5. **다음 행동**: 원인 제거를 위한 대안 3가지 이상 제안. 각 대안의 장단점과 예상 효과 포함

## 단계별 루프백 시나리오

### Stage 01 (Literature Review)
루프백 대상 없음 (최상위 단계). 같은 스테이지 내 재시도만:
- 검색 쿼리/전략이 부적절 → 검색 전략 수정 후 재수행

### Stage 02 (Framing)
**→ 01 (Literature Review)**:
- 식별한 gap이 실제로 존재하지 않음 → 추가 문헌 탐색 필요
- 프레이밍의 전제가 되는 선행 연구가 재현 불가/폐기됨 → 전제 재검토 필요

### Stage 03 (Planning)
**→ 01 (Literature Review)**:
- 실험에 필요한 baseline/데이터셋이 문헌에서 누락됨 → 문헌 보완 필요
- 계획된 평가 지표가 선행 연구와 비교 불가 → 비교 가능한 지표 체계 재조사

**→ 02 (Framing)**:
- novelty claim이 불명확 → 문제 정의 재수행
- 가설이 testable하지 않음 → research question 재정의

### Stage 04 (Analysis)
**→ 01 (Literature Review)**:
- 예상치 못한 데이터 특성이 문헌과 다름 → 해당 영역 재조사
- 분석 결과가 기존 문헌과 모순 → 모순 원인 파악 위해 문헌 재검토

**→ 02 (Framing)**:
- 가설 자체가 잘못됨 → research question 재정의
- novelty가 성립하지 않음 → 프레이밍 전면 수정

**→ 03 (Planning)**:
- 모델 아키텍처/학습 전략이 부적절 → 실험 설계 수정
- 평가 지표가 research question과 불일치 → 평가 전략 재설계
- 데이터 전처리/특성 엔지니어링 오류 → 설계 수준 수정

**같은 스테이지 내 재시도**:
- 하이퍼파라미터 튜닝 필요
- 구현 버그 → 수정 후 재실행
- 데이터 증강/샘플링 전략 수정

### Stage 05 (Interpretation)
**→ 01 (Literature Review)**:
- 결과 해석에 필요한 도메인 지식이 부족 → 해당 영역 문헌 보완
- 결과가 기존 패러다임과 충돌 → 패러다임 전제 재검토

**→ 02 (Framing)**:
- 결과가 원래 research question과 불일치 → 문제 재정의
- 클레임이 프레이밍 범위를 벗어남 → 프레이밍 수정

**→ 03 (Planning)**:
- 클레임을 뒷받침할 증거가 불충분 → 추가 실험 설계
- 한계점이 설계 수준에서 기인 → 실험 계약 수정

**→ 04 (Analysis)**:
- 클레임 정량화에 추가 분석 필요 → 분석 보완
- sensitivity analysis 부족 → 추가 분석 수행

## context.yaml 처리 (프로젝트 전환 시)
1. 기존 context.yaml을 `objects/history/context_{프로젝트명}_{날짜}.yaml`로 이관
2. 새 context.yaml을 새 프로젝트 용어로 작성
3. 이전 프로젝트 용어가 새 프로젝트에서도 유효하면 terms에 복사 (avoid는 초기화)
4. stages/에서 현재 research question과 무관한 섹션 전부 삭제
